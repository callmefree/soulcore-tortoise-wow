# 内容开发工作流 SOP（2026-08-22 起生效）

> 目标：**让每次游戏内容改动都经过 git 版本控制**，服务器可复现、改动可审查/回滚。
> 适用范围：SQL（数据库内容）、Lua（Eluna 脚本）、DBC（客户端附魔等）。

---

## 0. 一次改动的标准循环（新编号 → 提交 → 应用 → 记录）

```
[1] 写改动（新 SQL 迁移 / 改 Lua / 换 DBC）
[2] 本地校验（幂等检查、语法检查、能重放）
[3] git 提交（命名规范见 §3）
[4] 应用到服务器（deploy/ssh_soulcore.py --mysql* / --put，见 §4）
[5] 服务器验证（.reload eluna / 游戏内实测）
[6] 更新文档（迁移链 README「状态」列 + 现状文档 + 可选服务器快照）
```

原则：
- **只追加、不回改旧迁移**：改过的内容靠新编号文件表达，旧迁移保持历史原样。
- **迁移必须幂等可重放**（DELETE+INSERT / ON DUPLICATE KEY UPDATE / UPDATE 兜底），才能换机/重装恢复。
- **应用与提交都走 git 面**：禁止只改活服务器却不建 git 记录。

## 1. SQL 迁移链（`sql/local_changes/`）

- 当前最大编号 `023`，新改动续 `024`、`025`…
- 命名：`NNN_短横线描述.sql`（如 `024_irp_xxx.sql`）。
- 文件头注释含：来源、原因、目标库、前置、状态。模板：

```sql
-- ============================================================
-- 024_<描述>.sql
-- ============================================================
-- 目标库: tw_pb_world   前置: 023
-- 状态: ⏳ 待应用   （应用后改 ✅ + 日期）
-- 说明: <这次干什么>
```

- 应用后更新 `sql/local_changes/README.md` 表格「状态」列。

## 2. Lua / DBC 改动

- **Lua**：改动 `lua_scripts/{core,arpg,enchant}/` 下的脚本 → 提交 → `--put` 推到
  `/opt/soulcore-pb/server/bin/lua_scripts/` → `.reload eluna`（需 rank4）。
  新增脚本同时更新 `lua_scripts/README.md`。
- **DBC**：新 DBC 放 `dbc/` 下对应子目录（可读命名），提交；客户端侧重压 `patch-A.mpq`、
  清 `WTF/`+`WDB/` 缓存。DBC 与 SQL 的关联见子目录 README。

## 3. Git 提交规范

```text
<类型>: <一句话>

示例:
  feat(irp): 权重池新增 N 条词缀 (sql/local_changes/024)
  fix(lua): 超级炉石战斗状态拒绝传送
  perf(dbc): 重压 SIE 修复 X 附魔描述
  docs: 现状文档更新时间戳快照
```
- 一次提交聚焦一类改动；SQL 迁移链与配套 Lua/DBC 可同条提交（相关联）。
- 提交前检查不需要的口令/密钥（对已知口令值字样 `git grep` 应为空；口令走环境变量，禁止明文）。

## 4. 应用/部署命令（PB 服）

```bash
export SOULCORE_SSH_PASS='***' SOULCORE_DB_PASS='***'   # 见 deploy/README.md
# SQL：目标库自动解析（USE → 文件头「目标库」→ 默认 tw_world）
python deploy/ssh_soulcore.py --mysql-all sql/local_changes/017_phase1_reforge.sql
#   001-017 头标 tw_world/tw_logon（主服库族）；部署到 PB 实例时显式传库：--mysql-all 017_phase1_reforge.sql tw_pb_world
# Lua
python deploy/ssh_soulcore.py --put lua_scripts/core/welcome.lua /opt/soulcore-pb/server/bin/lua_scripts/welcome.lua
# 服务器验证/重启
python deploy/ssh_soulcore.py 'systemctl is-active pbmangosd pbrealmd'
```

## 5. 服务器事实同步（可选，建议每阶段一次）

```bash
python deploy/sync_server_baseline.py          # 探针+拉取+对比+快照
# 生成 docs/服务器现状_快照_<时间>.md，建议提交；对比报告仓库 vs 活服漂移
```

## 6. 备份纪律

- **周期 NAS 冷备**：`python deploy/run_backup.py`（主服+PB服、四库×2 → FNOS）。
- 重大改动前，可在 DB 内建备份表（`CREATE TABLE ... _bak AS SELECT ...`）便于快速回滚。
- 恢复流程见 `docs/reports/PB服冷备恢复指南_20260821.md`。

## 7. 环境准备（新机器/换机）

1. 安装 Python3 + `paramiko`。
2. 从记忆/交接清单拿到口令，`export SOULCORE_*`。
3. 克隆/恢复本仓库 → 按 `sql/local_changes/README.md` 说明重放迁移链。
4. 见 `_archive/项目文档与脚本_2026-08-19/md/切换电脑交接清单.md`。

## 8. 版本标签（里程碑锚点）

- 首个锚点 `v-baseline-2026-08-22` 已打在基线提交（`master`）；内容终态 = 重放 `001-023`，**pre-P2 = 重放 `001-017`**。
- 以后每完成一个 ARPG 阶段打 `v-phaseN-YYYYMMDD`（仅指向阶段完成点，不污染日常追加流）。
- 打标签：`git tag -a v-phaseN-YYYYMMDD -m "..."`。
