## 1. 为什么说“可行”—— 三层证据（源码级）

### 1.1 服务端真的在加载 IRP

`_archive/_audit/soulcore/src/game/Database/DBCStores.cpp:212`

```cpp
LoadDBC(..., sItemRandomPropertiesStore, dbcPath, "ItemRandomProperties.dbc");
```

`DBCStores.h:79` 声明了 `sItemRandomPropertiesStore`，`DBCfmt.h:46` 给出格式串 `nsiiixxssssssssx`，`DBCStructure.h:405-413` 定义了结构：

```cpp
struct ItemRandomPropertiesEntry {
    uint32 ID;
    char*  internalName;
    uint32 enchant_id[3];      // 2-4
    char*  nameSuffix[8];      // 7-14
};
```

> 思考题：为什么格式串里会有 `ssssssss`？它在解决什么问题？—— 提示：多语言后缀名。

### 1.2 内核真的在消费 `random_property`

- **表结构**：`tw_world_item_template.random_property mediumint(8) unsigned DEFAULT 0`（`create_databases.sql:6621` / `tw_world_item_template.sql:142`）
- **内存结构**：`ItemPrototype.h:474 uint32 RandomProperty; // id from ItemRandomProperties.dbc`
- **生成时机**：`Player.cpp` / `LootMgr.cpp: randomPropertyId = Item::GenerateItemRandomPropertyId(itemid)` → 掉落、拾取、StoreNewItem、交易、邮寄均会触发
- **权重抽取**：`ItemEnchantmentMgr.cpp:78 GetItemEnchantMod(entry)` → 查 `item_enchantment_template(entry, ench, chance)` 做加权随机
- **落盘字段**：`item_instance.randomPropertyId`（`Item.cpp: SaveToDB` / `LoadFromDB`）+ `ITEM_FIELD_RANDOM_PROPERTIES_ID` 网络同步
- **生效**：`Item::SetItemRandomProperties()` → `SetEnchantment(PROP_ENCHANTMENT_SLOT_0..2, ...)` → 客户端自动显示绿字与后缀名
- **校验**：`ObjectMgr.cpp:2246` 启动时校验 `proto->RandomProperty` 是否能在 `sItemRandomPropertiesStore` + `item_enchantment_template` 中找到，否则打 Error

> 小测验：`GetItemEnchantMod` 里 `chance` 累加到 `fCount` 再与 `rand_chance()` 比较，这是什么分布？如果某 entry 下三条记录 chance 分别是 50/30/20，被抽中的概率各是多少？如果总和 < 100% 会怎样？（看 `ItemEnchantmentMgr.cpp:101-112` 的二次抽样兜底）

2026-08-17 原生 IRP 扩充 2012 条已上线验证：工具链 `refine_db_grounded.py → gen_orange_sie.py → SIE_merged.dbc → build_patch_a.py → patch-A.mpq → restart pbmangosd` 全通。这直接证明 **SIE + IRP 双 DBC 同步更新**在你们这套编译与部署流程下无阻碍。

## 2. 路线对比：为什么原生 IRP 比 Lua 直写 SIE 更“稳”

| 维度 | 路线1：原生 IRP（本次） | 路线 B：Lua SetEnchantment（Orange 已上线） |
|---|---|---|
| 触发时机 | 内核在物品创建时自动 roll，无需脚本 | 依赖 lua_scripts/random_enchant.lua 四事件（3 登录/29 装备/32 拾取/36 接收） |
| 客户端显示 | 后缀名自动拼到物品名 + 3 绿字，纯 DBC 驱动 | 绿字靠 PERM_SLOT 附魔，名不变 |
| 性能 | 零 Lua 开销 | 每次登录全包扫描 Backfill |
| 维护 | 改 DBC + DB 池即可 | 需维护 Lua 白名单、bot 守卫、handler 首参 event 坑 |
| 存量追溯 | 已掉落物品不自动变，需补 `randomPropertyId` | Backfill 可追溯 |
| 适用场景 | 白/绿装随机词缀（魔兽原生语义） | 橙装式“额外特效” |

> 引导思考：什么场景下你会更想要“后缀名”而非“额外绿字”？（比如：玩家交易时一眼看出“熊之 xx”“虎之 xx”）

## 3. 落地四步法（与你现行 SOP 同构，只是把 SIE 换成 IRP+SIE+DB 三件套）

### 步骤 1 — 造池（SIE → IRP 打包）

- **输入**：Orange 战斗法术精炼池（已剔消耗品/制造/传送等，参考 `refine_db_grounded.py` 规则）
- **产出 A - SIE 增量**：每条战斗法术 → 1 条 `SpellItemEnchantment.dbc` 记录（`type[0]=3 EQUIP_SPELL, spell[0]=spellId, f21=4128894`），id 建议复用现有 `90001..` 稳定空间或新开 `80001` 段，**只增不重排**
- **产出 B - IRP 打包**：将 SIE 按 3 个一组打包为 `ItemRandomProperties.dbc` 记录：`enchant_id[0..2] = sie_id, nameSuffix = 中文后缀（如“之熊”“之虎”）`，id 新开 `1000+` 段（如 `50001..`），`internalName` 填英文标识
- **产出 C - 权重池**：`item_enchantment_template(entry, ench, chance)`，`entry = IRP_ID, ench = SIE_ID, chance = 权重`（等权 33.33 或按强度加权）

> 关键约束：IRP 的 `enchant_id` 指向的 SIE 必须同时存在于服务端与客户端 DBC，否则绿字不显示（与 SOP 铁律 2 同理）

脚本复用：
- `gen_orange_sie.py` 负责产 SIE（已通）
- 新增 `gen_irp_from_sie.py`（或在原脚本后追加 IRP 打包段）产 IRP + `item_enchantment_template.sql`

### 步骤 2 — 压 DBC（双 DBC 同步）

- 合并基线：服务端 `data/dbc/ItemRandomProperties.dbc`（基线 ~2000 条）+ 增量 IRP；服务端 `data/dbc/SpellItemEnchantment.dbc`（基线 1599 + 已有橙装 80001 段）+ 增量 SIE
- 工具：复用 `build_patch_a.py` 的最小 MPQ 写入器，同时写入 `DBFilesClient\ItemRandomProperties.dbc` 与 `DBFilesClient\SpellItemEnchantment.dbc` 到 `patch-A.mpq`
- 校验：`DBCFileLoader::GetFormatRecordSize == sizeof(T)`，`recCount +1, record 插入 string block 前, stringSize 累加`（DBC 铁律）

### 步骤 3 — 写 DB（赋池）

```sql
-- 3a 建池（幂等）
DELETE FROM item_enchantment_template WHERE entry BETWEEN 50001 AND 51000;
INSERT INTO item_enchantment_template (entry, ench, chance) VALUES
(50001, 90001, 33.33),
(50001, 90002, 33.33),
(50001, 90003, 33.34),
...;

-- 3b 赋池（示例：给 30-60 级白/绿装赋随机词缀，避开任务/消耗品）
UPDATE item_template SET random_property = 50001
WHERE quality IN (1,2) AND class IN (2,4)   -- 武器+护甲
  AND required_level BETWEEN 30 AND 60
  AND random_property = 0                   -- 不覆盖已有
  AND entry NOT IN (SELECT ... 剔除黑名单);

-- 3c 校验
SELECT random_property, COUNT(*) FROM item_template GROUP BY random_property;
SELECT entry, COUNT(*) c, SUM(chance) s FROM item_enchantment_template GROUP BY entry HAVING s NOT BETWEEN 99.9 AND 100.1;
```

> 提问：为什么 `random_property = 0` 的判断很重要？如果不加，会发生什么？（已附池装备被意外改池，但存量实例不受影响，造成新旧不一致）

### 步骤 4 — 双重启 + 验证

- **服务端**：`systemctl restart pbmangosd`（DBC 全量进内存，无 reload）
- **客户端**：覆盖 `Data/patch-A.mpq` → 重开客户端
- **存量追溯**（可选）：存量 `item_instance` 不会自动获得随机属性，需二选一
  - Lua Backfill：复用 `random_enchant.lua` 的登录扫描，对 `randomPropertyId=0` 且 `proto.random_property !=0` 的物品 `SetItemRandomProperties(GenerateItemRandomPropertyId(entry))`
  - SQL 补丁：离线维护期 `UPDATE item_instance SET randomPropertyId = ... WHERE ...`（需停服，避免在线脏写）

验证矩阵：

| 验证项 | 操作 | 预期 |
|---|---|---|
| 新掉落 | 击杀掉落白/绿装 | 物品名带后缀，悬停见 1-3 绿字 |
| 新创建 | `.additem <entry>` / 任务奖励 | 同上 |
| 权重分布 | 批量掉落 200 件 | 三词缀比例 ≈ chance 设定 |
| 持久性 | 装备后卸下/交易/存仓 | 后缀与绿字保留 |
| 回归 | 旧橙装（SIE 直写） | 不受影响（两套机制正交） |

## 4. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| DBC 与 DB 池不一致（IRP 指向不存在的 SIE） | 🔴 高 | 构建时交叉校验：每个 IRP.enchant_id 必须在 SIE_merged 中存在；启动日志 `ObjectMgr` 会报错 |
| 客户端 patch-A 未更新导致“只见名后缀无绿字”或反之 | 🟡 中 | 服务端与客户端 DBC 同源构建，发布时同版本打包，公告强制更新 |
| 权重和 < 100% 导致二次抽样偏差 | 🟢 低 | 构建脚本强制 `SUM(chance) = 100 ±0.1`，否则阻断发布 |
| DBC 损坏导致 `exit(1)` 无法启动 | 🔴 高 | 发布前备份 `*.dbc.bak.<ts>`，`LoadDBCStores` 失败立即回滚 |
| 存量装备不追溯引发“新旧不一致”投诉 | 🟡 中 | 明确运营口径：仅新产出生效；或择期 Lua Backfill 一次性补 |

## 8. 结论复述

> 回到最初的问题：“利用 `item_template.random_property` 填 IRP 编号，内核自动套词缀，是否可行？”
>
> **可行，且是你们基座上最稳的一条路。** 它把随机性交还给内核的加权抽样，把显示交还给 DBC 的后缀与附魔，把运营交还给 DB 的 `random_property` 赋池——没有 Lua 常驻，没有事件号坑，没有背包扫描开销。你们 08-17 的 2012 条已证明工具链是通的，剩下的只是把“SIE 直写”换成“IRP 打包+权重池”这一步。
